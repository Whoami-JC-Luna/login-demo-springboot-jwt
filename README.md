## 1. Overview

A backend REST API demonstrating secure authentication and role-based access control with Spring Boot and JWT. Built with real-world practices throughout: OWASP guidelines (2025), clean layered architecture, and a test suite covering the main flows.

Frontend and deployment are currently in development. This README focuses on the backend, which is the main scope of the project right now.

---

## 2. What This Project Does

Users can register, log in, and interact with two resources:

- **Quotes** — A collection of inspirational quotes. Users can create, edit, search, and delete their own. Includes a random quote endpoint and accent-insensitive search.
- **Signatures** — A guestbook. Each user can write one signature message, and update or delete it at any time. Anyone can read the guestbook without logging in.

Access is controlled by three roles:

- `ROLE_GUEST` — unauthenticated access, read-only endpoints
- `ROLE_USER` — registered user, can manage their own content
- `ROLE_ADMIN` — full management access

Roles are assigned server-side only — the client cannot choose or escalate its own role.

## 4. Architecture

The project follows a standard layered architecture:

```
controller → service (interface + impl) → repository → database
               ↕
        dto / mapper / model
```

Each layer has a single responsibility. Controllers handle HTTP, services handle business logic, and repositories handle data access.

### Why interfaces for services?

Using interfaces (`AuthService`, `QuoteService`, etc.) instead of injecting the concrete class directly allows swapping implementations without touching the controllers, and makes unit testing with mocks straightforward.

### Why constructor injection instead of @Autowired?

Constructor injection makes dependencies explicit, supports immutability (`final` fields), and is the approach recommended by Spring itself. Lombok's `@RequiredArgsConstructor` generates the constructor automatically, keeping the code clean.

### Why MapStruct for DTO mapping?

MapStruct generates the mapping code at compile time, so there is no runtime reflection. This is faster than alternatives like ModelMapper, and critically — if a field mapping is missing or incorrect, it fails at compile time, not at runtime.

### How Lombok is used

Lombok eliminates boilerplate Java code through annotations processed at compile time. The generated bytecode is identical to what you would write manually — there is no runtime overhead.

Key annotations used in this project:

- `@RequiredArgsConstructor` — generates a constructor for all `final` fields. Combined with constructor injection, this is what replaces the manual constructor in every service and component.
- `@Getter` / `@Setter` — generates accessors for entity and DTO fields without cluttering the class body.
- `@Builder` — generates a builder pattern for DTOs and response objects, making object construction more readable.
- `@Data` — shorthand for `@Getter`, `@Setter`, `@ToString`, `@EqualsAndHashCode`. Used on simple DTOs where all of these are needed.
- `@NoArgsConstructor` — required by JPA on entity classes, which need a no-argument constructor to instantiate objects from database rows.

Lombok is a compile-time tool — it has no impact on runtime performance and does not add any dependency to the final jar beyond the annotation processor used during the build.

## 6. Security Decisions

Security was a primary focus during development, following the OWASP Top 10 (2025).

### Authentication (JWT)

- Tokens signed with HMAC-SHA256
- Secret key loaded from environment variable — never hardcoded
- Token expiration set to 1 hour
- Filter runs once per request (`OncePerRequestFilter`) and validates the token before allowing access

### Passwords

- Hashed with BCrypt before storing (OWASP A04 — Cryptographic Failures)
- Policy enforced via regex at registration:

```
^(?=.*[a-z])(?=.*[A-Z])(?=.*\d)(?=.*[@$!%*?&#._\-])[A-Za-z\d@$!%*?&#._\-]{8,}$
```

Requirements: minimum 8 characters, at least one lowercase letter, one uppercase letter, one number, and one special character (`@$!%*?&#._-`).

No maximum length is enforced — aligned with OWASP and NIST guidelines, which explicitly recommend against arbitrary password length limits.

### Access control

- Roles: `ROLE_GUEST`, `ROLE_USER`, `ROLE_ADMIN`
- Roles are assigned server-side only. The client cannot choose a role during registration (OWASP A01 — Broken Access Control)
- Resource ownership is verified before any update or delete. If a user tries to modify a quote that is not theirs, the API returns `404` — not `403` — to avoid revealing that the resource exists (OWASP A01)

### User enumeration prevention

- Login and registration return generic error messages. An attacker cannot determine whether an email is already registered (OWASP A07 — Authentication Failures)

### Stateless sessions

- No server-side sessions. The API is fully stateless — all authentication context comes from the JWT on each request.

### JWT role lookup

The JWT filter queries the database on every request to retrieve the user's current role, rather than embedding the role in the token. This is an intentional trade-off: consistency over performance. If a user's role changes, the new role takes effect immediately without waiting for the token to expire.

## 7. OWASP Top 10 2025 — Applied

| Category | Application in this project |
|---|---|
| A01 — Broken Access Control | Roles assigned only in backend. `findByIdAndUser` returns 404 for both non-existent and unowned resources. No information leaked about resource ownership. |
| A03 — Software Supply Chain Failures | Dependency vulnerability GHSA-72hv-8253-57qq identified, evaluated, and documented. Impact assessed as low (see Known Issues section). |
| A04 — Cryptographic Failures | Passwords hashed with BCrypt. JWT signed with HMAC-SHA256. Secret key excluded from repository. |
| A07 — Authentication Failures | Generic error messages on login and registration. No session state on server. Token expiration enforced. |
| A09 — Security Logging & Alerting Failures | Detailed internal logs for all critical operations. Generic messages returned to the client — internal details remain server-side only. |

*Logging criteria applied consistently: `log.warn` for expected business situations (404, 409). `log.error` reserved for unexpected system failures. Internal log detail never exposed to the client.*

## 8. DTOs & Validation

The API never exposes entity classes directly. Every request and response goes through a dedicated DTO, keeping the internal model decoupled from the API contract.

### Request DTOs

Input validation is enforced via Jakarta Bean Validation on all request DTOs:

| DTO | Validations |
|---|---|
| `RegisterRequest` | Username 4–10 chars, valid email format with TLD required (e.g. `.com`, `.es`, `.io`), password matching full regex policy |
| `LoginRequest` | Email and password not blank |
| `QuoteRequest` | Text and author not blank |
| `SignatureRequest` | Message and author not blank |

### Response DTOs

Response DTOs expose only the fields the client needs — no passwords, no internal IDs unless necessary, no Hibernate proxies leaking into the response.

### Mapping

Mapping between entities and DTOs is handled by MapStruct, which generates the conversion code at compile time. This avoids runtime reflection and catches mapping errors early — if something does not map correctly, the build fails before the application ever runs.

## 9. Exception Handling

The project uses a set of custom exceptions mapped to specific HTTP status codes, handled centrally by a `@RestControllerAdvice` class (`GlobalExceptionHandler`). This keeps error handling out of the controllers and ensures consistent responses across the API.

| Exception | HTTP Status | When |
|---|---|---|
| `InvalidCredentialsException` | 401 | Wrong email or password on login |
| `UserAlreadyExistException` | 409 | Email already registered |
| `QuoteNotFoundException` | 404 | Quote not found or not owned by the user |
| `SignatureNotFoundException` | 404 | Signature not found |
| `SignatureAlreadyExistException` | 409 | User tries to create a second signature |

**Why 404 instead of 403 for ownership errors?** Returning 403 would confirm that the resource exists but the user cannot access it. Returning 404 avoids revealing that information (OWASP A01 — Broken Access Control).

Validation errors (`@NotBlank`, `@Email`, etc.) return `400` with a map of field-level messages, so the client knows exactly which fields failed.

Unhandled exceptions fall through to a generic `500` handler that returns a safe message with no internal details exposed.

## 10. Database Migrations

Database schema changes are managed with Flyway. Each migration is versioned and runs in order on startup. This ensures schema consistency across environments without manual SQL scripts.

| Migration | Description |
|---|---|
| V1 | Initial table creation (users, quotes, signatures) |
| V2 | Add `created_at` to users |
| V3 | Seed initial quotes data |
| V4 | Rename columns to English (`texto → text`, `autor → author`) |
| V5 | Assign all seeded quotes to admin user |
| V6 | Add PostgreSQL `unaccent` extension for accent-insensitive search |
| V7–V8 | Signatures table and timestamps |
| V9 | Create admin user via migration (ensures reproducibility across environments) |
| V10 | Add trigger to auto-update `updated_at` on signature changes |
| V11 | Create guest user via migration, using `WHERE NOT EXISTS` for idempotency |

### Date management

Timestamps (`created_at`, `updated_at`) are managed entirely by the database, not by Hibernate. `created_at` uses `DEFAULT now()` in the migration. `updated_at` uses a PostgreSQL trigger to update automatically on every row change.

This is more reliable in production than relying on the application layer, as it is independent of the application server's timezone and Hibernate's lifecycle events. Switching to Hibernate-managed timestamps would only require removing annotations — the reverse migration would be more complex.

## 11. Search Feature

Quote search supports accent-insensitive matching using the PostgreSQL `unaccent` extension. For example, searching for `cafe` will also match `café`. This is handled with native queries in the repository layer, since JPQL does not support database-specific functions.

Native queries with pagination require an explicit `countQuery` — this is not automatic and must be defined separately in the annotation.

Search uses `LIKE %text%` (contains) rather than `startsWith`. This was a deliberate UX decision: users expect to find a quote by any word it contains, not just the beginning.

## 12. Testing

The project has tests at multiple levels:

- **Unit tests** — Services tested in isolation using Mockito mocks
- **Controller tests** — Each controller tested with `@WebMvcTest`, mocking the service layer
- **Security tests** — Separate test classes for JWT filter behavior and role-based access control
- **Context test** — Verifies that the Spring application context loads correctly

Tests run against an H2 in-memory database with Flyway disabled, so they are fast and do not require a running PostgreSQL instance.

### Bug detected and fixed by tests

During the implementation of `JwtService` tests, a real production bug was identified.

The `validateToken()` method did not catch `ExpiredJwtException`. When a user sent an expired token, the exception propagated up to Spring, which converted it into an HTTP `500` (Internal Server Error).

**Impact:** the client received a generic `500` instead of a `401 Unauthorized`, had no indication that it needed to re-authenticate, and a `500` response can expose internal server details.

**Fix:** a specific `catch` for `ExpiredJwtException` that returns `false` instead of propagating the exception. The specific exception type was intentional — catching a generic `Exception` would hide other real errors.

*This is a concrete example of tests catching bugs that manual Postman testing missed.*

## 13. Known Issues & Dependencies

### GHSA-72hv-8253-57qq — jackson-core (severity 7.5)

A vulnerability was identified in `jackson-core`, a transitive dependency pulled in by `jjwt-jackson`. It involves a bypass of the `maxNumberLength` limit in the asynchronous parser that can cause a Denial of Service (DoS).

**Impact assessment: LOW in this project.**

- The vulnerability exclusively affects the asynchronous Jackson parser
- This project uses Spring MVC (synchronous), not Spring WebFlux (reactive/async)
- The vulnerable parser is never executed in this stack

The vulnerability is transitive — the version of `jackson-core` is not controlled directly from this project's dependencies, but through `jjwt-jackson`. This maps to OWASP A03:2025 — Software Supply Chain Failures.

Action taken: documented and assessed. Will be monitored for an upstream fix in `jjwt-jackson`. No immediate action required given the zero practical impact in this architecture.

### JWT role lookup per request

The JWT filter queries the database on every authenticated request to retrieve the user's current role. This is an intentional design decision: consistency is prioritized over performance at this stage. If a user's role is updated, the change takes effect immediately without waiting for token expiration.

## 14. Running Locally

**Requirements:** Java 17, Maven, PostgreSQL 17

1. Clone the repository
2. Copy `application.properties.example` to `application.properties` and fill in your database credentials and JWT secret
3. Start PostgreSQL and create the database
4. Run the application:

```bash
cd backend/auth-api
mvn spring-boot:run
```

Flyway will apply all migrations automatically on startup. This includes creating the admin and guest demo users.

**Optional:** a `docker-compose.yml.example` is included if you prefer to run PostgreSQL in a container:

```bash
docker-compose up -d
```
